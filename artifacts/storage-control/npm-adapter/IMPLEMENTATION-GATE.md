# npm cache verification: production adapter gate

30 September 2026 · Status: **guidance only; no production adapter or mutation route enabled**.

The [isolated fixture](../measurement/npm-spike/DECISION.md) showed that `npm cache verify` removed one unreferenced 4 MiB content blob, retained the referenced package and left a sibling sentinel alone. A second verification reclaimed nothing. This proves a possible narrow benefit, not a repeatable saving on a real cache. No personal npm cache was read or modified for this assessment.

## Why the existing executor cannot safely run it

1. **The target is not established.** The scanner observes `~/.npm/_cacache`, but [npm's cache setting](https://docs.npmjs.com/cli/cache/) is configurable. [npm configuration precedence](https://docs.npmjs.com/cli/v11/using-npm/config/) includes command-line options, environment variables, project, user and global files. A path measured in one context need not be the cache used by another project or shell. A displayed default path is not consent to maintain whichever path npm later resolves.
2. **The current runner cannot constrain npm.** `ToolRunner.runExecutable` supplies arguments and a timeout but inherits the app's environment and working directory. `npm_config_*`, `NODE_OPTIONS` and npmrc files can alter execution. An adapter needs a dedicated child runner with a deliberately constructed environment, fixed neutral working directory, explicit `--cache`, empty isolated user/global config, closed stdin, bounded output and deadline. It must validate the actual npm executable/version; a shell shim or executable changing between review and run cannot be silently trusted.
3. **Other writers are not coordinated.** `ScanGate` serializes Cairn operations only. `RunningApps` lists GUI bundle IDs, not all npm/Node/IDE processes and their configured cache roots. A process-name or open-file snapshot can miss a writer or race a new one. [cacache's README](https://github.com/npm/cacache/blob/main/README.md) describes lockless concurrent cache access and resilience to process races, but its `verify` operation also garbage-collects unreferenced content and removes its temporary directory. That general claim does not establish that `npm cache verify` is safe alongside every supported npm CLI writer. The reviewed npm documentation provides no cross-process maintenance lock for Cairn to acquire. Until the verify/write interaction is proven for supported versions, active **or unknown** writer state must be treated as ineligible. The PRD explicitly requires this; a best-effort `pgrep` check is insufficient.
4. **This is permanent, with no Cairn Put Back.** `verify` may garbage-collect cache content. The existing Trash recovery path does not apply. It needs explicit review of the exact cache/version, permanent scope, possible redownload/offline cost and zero-benefit possibility. `ActionJournal` can record an intent and outcome, but its generic uncertain-action reconciliation currently speaks in original/Trash paths. An npm-specific interrupted outcome must not be replayed automatically or shown as restorable.
5. **A scanned byte total is not savings.** `CleanupAccounting.toolBytes` accepts an affected-size estimate; the full cache size would be a false reclaim number. Use a same-volume before/after available-capacity reading (`CleanupCapacityChange`) and show zero, negative or unavailable changes. The observed capacity delta can include other processes, APFS snapshots or purgeable-space changes; it cannot be attributed solely to Cairn. npm's output should be retained only as bounded diagnostics, not as a stable byte-count API.

## Smallest eligible adapter contract

- Default-off capability, separate from generic `.tool` and `Cleaner`; never turn the existing advice-only npm scanner row into `.trash`. An explicit reviewed action names **one** cache root, its observed identity/volume, npm executable identity and tested version, evidence time, exclusions and consequences. No blanket `~/.npm` deletion, no `npm cache clean --force`.
- At review and again immediately before execution, canonicalize each path component; reject symlinks, aliases/redirects, protected or excluded ancestors/descendants, missing/replaced volumes, unowned/unwritable roots and unsupported npm versions. Require the selected cache to match the explicit `--cache` passed to a constrained child. Do not infer all project caches from the default context.
- Prove an idle-cache contract for each supported npm version or remain guidance-only. If a supported lock exists, acquire it around final identity/writer validation and `verify`; otherwise a process snapshot must not be treated as proof. Do not quit npm, IDEs or databases to make the check pass.
- Acquire `ScanGate` for the whole operation. Prepare the durable journal and write an intent **before** launching npm. A cancelled/failed/uncertain child must settle before releasing the gate. Never retry automatically after an uncertain outcome. Persist the outcome before showing completion.
- Read available capacity on the selected cache's volume before and after, requiring a matching volume UUID. Show the signed observed change, no Undo, action status and whether the user's storage goal was actually met. Keep `affectedBytes` unknown unless separately measured under a bounded, validated method.

## Certification fixtures and decisions still required

| Gate | Evidence required before enabling |
|---|---|
| Configuration and target | Default, environment, project, user and global overrides; two simultaneous cache roots; symlinked/redirected/protected/excluded cache; executable replacement; changed npm version; external drive removed/replaced during review and startup. Exact reviewed root is the only target. |
| Concurrency | Concurrent `npm install`/`cache add` using the **same** cache; IDE/child npm, process-enumeration denial and a writer starting after preflight. Show a supported lock/safety guarantee or keep the route blocked. |
| Process boundary | Sanitized environment, neutral cwd, no scripts/network, bounded output and time, cancellation/timeout/kill settled before gate release. Run only in disposable fixtures. |
| Journal and receipt | Inject failures before intent, after intent, during verification, before outcome and at capacity sampling; restart leaves uncertainty visible and never replays. Healthy cache returns zero; positive, negative and unavailable same-volume capacity outcomes remain truthful. |
| Product decision | Explicitly approve a permanent, no-Undo npm maintenance action with possible redownload/offline cost and potentially zero reclaim. Independent safety review and a controlled end-to-end run precede public claims. |

## Decision

Do **not** implement an executable production adapter in this pass. The strongest remaining blocker is the unproven writer contract, followed by exact-target/environment and npm-specific recovery semantics. Adding a default-off file that can invoke npm would not certify or improve the user-facing capability, and could be accidentally routed later. Keep the existing advice-only guidance and run the dedicated fixture work above before revisiting this decision.
